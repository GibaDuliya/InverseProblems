# План реализации протокола обучения и оценки SOC

## Результат

Команда `bridge-soc-train --config configs/soc/train.yaml` должна дообучать ученика на полном тренировочном сплите учителя, валидировать через заданное число обновлений Adam и тестировать единственную модель с максимальной средней валидационной наградой. Основной интерфейс продолжения — та же команда с `--resume runs/soc/<name>/checkpoints/last.pt`. Для реального запуска пользователь указывает существующий checkpoint учителя.

Это продолжение уже реализованного [алгоритма AM](soc_implementation_plan.md). Использовать существующие `initialize_control_denoiser`, `adjoint_matching_loss`, `SOCSampler` и `JPEGConsistencyReward`. Сохранить знаки, сетку времени, перенос adjoint, выбор времени отдельно для каждого изображения и режим сети ученика при вычислении AM. Учитель по умолчанию инициализируется из EMA базового моста. Для ученика во всех операциях используются текущие веса Adam (raw). EMA ученика в объём задачи не входит.

Сейчас `SOCTrainer.validate` усредняет только reward первых нескольких val-батчей, а `fit` обновляет один `last.pt`. Целевой протокол добавляет полную оценку восстановления, визуализации, отбор и финальный тест, сохраняя возможность продолжения из последнего состояния.

## 1. Сначала определить цикл обучения

Основной файл — `src/bridge_soc/training.py`. Сначала выразить в `SOCTrainer.fit` следующий порядок операций. Это задаёт контракт оценщика и чекпоинтов.

1. Продолжить детерминированный обход train с сохранённой позиции. Каждый проход — полная перестановка ID из манифеста через существующий `EpochSampler.set_epoch`. Очередная валидация не начинает новый проход.
2. Взять до `grad_accum_steps` последовательных микробатчей, ограничив группу концом прохода. Обнулить градиенты один раз. Для каждого микробатча из B изображений вызвать существующий AM loss со своим обучающим rollout, выполнить backward с весом B / G, где G — фактическое число изображений во всей группе. AM loss уже усреднён внутри микробатча. Удобно собрать группу на CPU, посчитать G и переносить на устройство по одному микробатчу. Граф предыдущего rollout освобождается до обработки следующего. Аналогично взвесить train loss и train reward для журнала.
3. Один раз вызвать Adam.step(), увеличить `step` на один и `samples_seen` на G, сохранить позицию следующего микробатча. Неполный микробатч и неполную группу в конце прохода обработать. `step` во всех интервалах обозначает завершённые обновления оптимизатора.
4. На первом шаге и при кратности `log_interval` добавить в `metrics.jsonl` шаг, loss, reward, samples_seen и позицию в проходе.
5. При кратности `validation_interval` или на последнем шаге провести валидацию, если этот шаг ещё не оценён. Записать отчёт и агрегаты, сравнить среднюю reward с историческим максимумом, при улучшении обновить best. Сравнение строгое, первое конечное значение выигрывает, в том числе отрицательное. Неконечная награда — ошибка оценки.
6. При кратности `checkpoint_interval` и при штатном завершении записать last. Если события совпали, сначала выполнить пункт 5. При необходимости остановки завершать на границе optimizer step.
7. После финальной записи last загрузить raw-ученика из best в модель для оценки, выполнить тест и сохранить отчёт. Загрузка best для теста не должна менять содержимое last. При продлении завершённого запуска провести финальный тест по результату нового бюджета и обновить `test/reward`. Предыдущий тест не участвует в отборе.

Рабочий конфиг должен давать хотя бы один полный проход по train. Предлагаемый удобный смысл `max_steps: null` — вычислить бюджет одного полного прохода как ceil(len(train_loader) / grad_accum_steps). Положительное целое задаёт точный бюджет, включая короткий smoke-запуск или несколько проходов. При старте вывести эффективный лимит, число изображений train и шагов на проход. Если задан меньший лимит, явно показать, что запуск частичный. Рабочие интервалы измеряются в шагах даже при автоматически вычисленном бюджете. Если предоставляется ранняя остановка, по умолчанию она выключена; считать терпение в завершённых валидациях и разрешать остановку только после первого полного прохода. В базовой реализации достаточно остановки по бюджету.

## 2. Конфиг и сборка эксперимента

Изменить `src/bridge_soc/config.py`, `src/bridge_soc/train.py` и `configs/soc/train.yaml`. Пример целевого рабочего конфига:

```yaml
seed: 42
output_dir: runs/soc/jpeg
control:
  teacher_checkpoint: runs/my_teacher/checkpoints/last.pt
  teacher_weights: ema
  mode: abm
sampling:
  clip_output: true
reward:
  name: jpeg_consistency
  input: clipped
training:
  device: cuda
  beta: 1.0
  lr: 0.00001
  batch_size: 1
  grad_accum_steps: 1
  max_steps: null
  log_interval: 1
  validation_interval: 100
  checkpoint_interval: 100
evaluation:
  batch_size: 8
```

- Согласовать default `batch_size: 1` в dataclass и YAML. `evaluation.batch_size` независимо регулирует память оценки. Положительные интервалы и accumulation валидировать при загрузке.
- Добавить SOC-секцию частичных evaluation overrides. Наследовать из **конфига в checkpoint учителя** размеры val/test, subset_seed, visual paths, input_baseline и конфиги метрик обоих сплитов. Разрешить явное переопределение этих полей. Для размеров различать отсутствие ключа (наследовать) и явный null (весь сплит). Веса оценки ученика всегда raw, расписание — training.validation_interval, критерий — reward/max, финальный тест включён. Не переносить управляющие флаги, criteria, EMA или epoch interval учителя. Если у старого учителя нет описания полноценного протокола, для CelebA взять профиль из `configs/celeba_medium_abm_T1.yaml`; для пользовательского датасета разрешить явный профиль с собственными метриками и визуальными ID.
- Для CelebA medium ожидаются 512 val и 1024 test, для основной серии 512 и 4096. В работе использовать фактический профиль учителя. Для небольшого тестового датасета явно задать подходящие размеры, метрики и visual paths. Проверить валидность ID для сплита, размер подвыборки, размер панели и достаточность тестовой выборки для настроенного KID. Старое поле `validation_batches` заменить оценкой по ID; при явном использовании в старом YAML дать понятное сообщение о переходе на `evaluation.subset_size`.
- Переиспользовать `build_soc_data` и проверку `split_checksum` и corruption учителя. Checksum — SHA-256 канонического JSON манифеста, включающего списки ID, группы и параметры разбиения. Записать split.json и эффективный config.yaml с разрешёнными sampling/evaluation, бюджетом и источником весов. На resume сравнивать эффективные настройки и проверять, что фиксированные выборки и модель совпадают.

## 3. Одна генерация для всех метрик и панелей

Создать `src/bridge_soc/evaluation.py` для SOC-части оценки. За образец взять `src/bridge_restore/evaluation/{evaluator,report,visualization,selection}.py`. Переиспользовать существующие построение subset, реестр обычных метрик, EvaluationReport и формат панелей. Если нужен общий код, извлечь выбор индексов или добавить в RestorationEvaluator небольшой опциональный обработчик батча с доступом к результату генерации. Существующие вызовы оценщика, SDESampler и CLI моста должны проходить прежние тесты. JPEG reward требует метаданных всего SOC-батча; добавлять её в обычный реестр метрик моста с одним только MetricBatch не следует.

1. Один раз зафиксировать ID val и test существующим алгоритмом: сначала включить все ID из соответствующего JSON панели, затем добрать без повторов с subset_seed. Сохранить их порядок для воспроизводимости. Никаких тестовых результатов до завершения обучения.
2. Оценивать при eval/no_grad. На каждом батче получить raw-терминал через `SOCSampler.sample(..., generator=..., clip_output=False)`. Вычислить поизображенческую reward через `reward(reward_image(terminal, reward.input), batch)`. Для метрик и панелей взять тот же terminal, применив clamp только согласно `sampling.clip_output`. Не делать второй rollout ученика. Вызванный внутри JPEG reward использует DCT-метаданные именно этого наблюдения. Проверить форму, конечность и число полученных наград.
3. Изолировать оценку от генераторов обучения, включая создание DataLoader/метрик и случайность KID. Для каждого сплита использовать фиксированный evaluation seed и неизменный порядок батчей. В начале каждого прохода оценки сбрасывать отдельный генератор rollout. Учитель и ученик на одном сплите должны видеть совпадающий шум. Кэшировать по ID награду замороженного учителя в рамках запуска (при resume можно воспроизводимо пересчитать). На тесте впервые посчитать её при финальной оценке. Для сравнения с учителем также использовать SOCSampler.
4. Средняя награда = сумма наград всех реконструкций / число изображений. В summary записать `restoration.reward.mean`, среднюю награду учителя и разность средних; в per_image — sample_id и индивидуальные reward. Отбор использует только `restoration.reward.mean`. Исходный JPEG baseline для обычных метрик вычислять по правилам bridge_restore.
5. Стандартные val-метрики CelebA — PSNR, SSIM, LPIPS-Alex, ArcFace, MUSIQ. На test также FID, KID, observation_mse, observation_mae. Учитывать параметры метрик учителя, включая покрытие ArcFace и subset_size KID. FID и KID — агрегаты. Освободить валидационные metric-сети перед созданием тестовых, как в bridge_restore.
6. Визуальные ID CelebA берутся из `configs/visual_samples/celeba_val.json` (16) и `celeba_test.json` (32). Это часть оценочной выборки. Сохранять по восемь строк на PNG, колонки clean / observation / restoration. Best получает те же реконструкции, что вошли в выигравший отчёт.

## 4. Результаты, сохранение и resume

Целевое дерево после нескольких валидаций:

```text
runs/soc/<experiment_name>/
  config.yaml
  split.json
  metrics.jsonl
  checkpoints/
    last.pt
  validation/
    step_00000100/
      summary.json
      per_image.jsonl
      protocol.json
      images/panel_00.png ... panel_01.png
    step_00000200/             # тот же формат
  best/
    reward/
      checkpoint.pt
      summary.json
      per_image.jsonl
      protocol.json
      images/panel_00.png ... panel_01.png
  test/
    reward/
      summary.json
      per_image.jsonl
      protocol.json
      images/panel_00.png ... panel_03.png
```

Каталог валидации всегда именуется по шагу, включая границу прохода. История отчётов растёт; полные состояния хранятся только в last и best. В protocol.json фиксировать step, split, checksum, все оценённые ID, visual ID, профиль метрик, метод и seed шума, sampler и NFE, reward.input, clip_output, тип весов raw и идентификатор учителя. Для test записать шаг и значение критерия выбранного чекпоинта.

В `src/bridge_soc/checkpoint.py` и `training.py` обеспечить следующее:

- Оба файла — полноценные состояния на границе optimizer step. Сохранять student, Adam, effective config, teacher provenance, архитектуру, bridge/sampling/data, step, samples_seen, курсор следующего train-микробатча, состояния RNG, включая генератор rollout, лучший val step/value и last_validation_step. Для записи использовать атомарный `save_checkpoint` из bridge_restore. Сохранить совместимость формата с общим загрузчиком (сейчас он требует format_version=1); при необходимости добавить отдельную версию SOC-состояния.
- Курсор при accumulation хранить явно. Восстановление детерминированной перестановки, позиции и RNG должно давать те же последующие обновления. Увеличение max_steps допустимо. Изменение split, учителя, reward, sampler, параметров оптимизации и evaluation-протокола при продолжении проверять до записи в каталог. При возобновлении после финального теста освободить/переинициализировать временное состояние оценщика.
- Проверить согласованность исторического best с записанным в last шагом. Учесть прерывание между валидацией и следующей периодической записью last: простое решение — дополнительно сохранять last при каждой завершённой валидации. Если прервана сама публикация отчёта/best/last, при восстановлении распознавать неполную запись и согласованно завершать или переигрывать её; повторная обработка шага не должна терять предыдущий максимум или удваивать историю. При отсутствии необходимых исторических файлов сообщать конкретную причину. Не считать число строк лога курсором обучения.
- Не нарушать `load_student` для уже существующих SOC-чекпоинтов. Старый last содержит raw student, Adam, RNG и позицию при accumulation=1, но не историю новой оценки. Для него явно описать переход: после проверки совместимости восстановить обучение, оценить восстановленные веса как первую точку нового протокола и инициализировать best. Сохранить прежний format для инференса и протестировать переход отдельно.

## 5. Проверка готовности

Расширить `tests/bridge_soc/test_soc_training.py` и добавить тесты оценщика в `tests/bridge_soc/`. Использовать маленькие CPU-модели/данные и лёгкие метрики, контролируемую reward для проверки отбора. Реальные тяжёлые метрики уже имеют собственные тесты.

- Пример для accumulation: пять изображений, batch_size=2, grad_accum_steps=2 дают обновления по четырём и одному изображению. Проверить порядок ID, нормировку, samples_seen=5 и переход к новой перестановке. Валидация внутри прохода не пропускает изображения.
- Неполный evaluation-батч: среднее reward совпадает с ручной суммой по всем ID. Изменение reward.input меняет вход награды независимо от clip_output. Счётчик rollout подтверждает одну генерацию ученика на батч; одинаковые веса учителя и ученика дают совпадающие результаты при фиксированном шуме. Проверить ID панелей, содержимое отчётов и раздельность val/test.
- Задать val rewards с максимумом в середине запуска, равенством и последующим ухудшением. Проверить шаг best, шаг last, идентичность best-панелей выигравшим val-панелям, загрузку для теста именно best и сохранность last после теста. Включить финальный шаг между интервалами и шаг, где интервалы совпадают.
- Сравнить непрерывный CPU-запуск с прерванным и продолженным из last в середине прохода с accumulation. Сверить веса, Adam, курсор, samples_seen, генератор rollout, исторический best и следующий train-батч. Отдельно покрыть resume после завершения с увеличенным бюджетом и восстановление после неполной записи. Оставить прежнюю проверку самостоятельного инференса без файла учителя.
- Обновить `docs/soc_training.md`: рабочий конфиг, требования для JPEG и выбранных quality-метрик, команды старта/resume и дерево результатов. Прогнать `python -m pytest tests/bridge_soc -q`, затем `python -m pytest -q` в окружении проекта. Для сквозного теста установить extras согласно pyproject.toml; явно указать пропуски тяжёлых проверок. В результате сообщить отдельно, выполнен ли реальный прогон CelebA/GPU.
