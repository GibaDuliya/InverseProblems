## Как согласовывать работу с пользователем

Перед удалённой операцией модель показывает точную команду целиком и коротко объясняет её эффект. Для чтения указывает, какие журналы, конфиги или задания будут проверены. Для передачи перечисляет исходные пути, назначение и возможную перезапись. Для запуска сообщает модель, конфиг, GPU, лимит и зависимости. Для удаления показывает точные пути и что в них находится.

- Для каждой SSH-операции отправлять отдельный запрос на разовое разрешение, включая повтор после ошибки. В Codex для этого используется `exec_command` с `sandbox_permissions: "require_escalated"` и понятным `justification`. Постоянное правило разрешения не требуется.
- Доступ пользователя через SSH и разрешение Codex на конкретную команду — два отдельных шага. Парольную фразу ключа пользователь вводит только в своём терминале Mac. Пароль и приватный ключ в чат не передаются.
- Сначала сверять локальные файлы и текущий статус, затем показывать конкретный план операции. Перед запуском проверить конфиг и свободный путь результатов. После запуска сохранить ID и проверить фактическое состояние задания.
- Если пользователь просит только посмотреть статус, достаточно чтения очереди, учёта и логов. Если просит скачать результаты, сначала установить, какие отчёты готовы. Если просит удалить эксперименты, сначала провести инвентаризацию, затем согласовать точный список для удаления.
- Одно согласованное SSH-соединение может наблюдать за заданием циклом, если заранее показаны команда, интервал и условие выхода. Обычный интервал сообщений о прогрессе при долгой передаче или мониторинге — около двух минут, если пользователь не указал другой.

## SSH с Mac

Алиас `zhores` уже используется. Обычная автоматизированная команда подключения выглядит так:

```bash
ssh -o BatchMode=yes -o ConnectTimeout=10 zhores hostname
```

`BatchMode=yes` отключает интерактивный запрос пароля. Если свежий вход отклонён с `Permission denied`, пользователь может снова загрузить ключ своей парольной фразой. Эти команды он выполняет в терминале **на Mac**:

```bash
ssh-add -t 1h ~/.ssh/id_ed25519_zhores
ssh -o BatchMode=yes -o ConnectTimeout=10 zhores hostname
```

Первый вызов делает ключ доступным локальному `ssh-agent` на час. Второй проверяет новый вход. Успешный ответ обычно выглядит как имя login-узла, например `an01`. Уже открытое SSH-соединение может работать и после истечения срока ключа. При `Operation timed out` сначала отличить сетевой тайм-аут от отказа аутентификации и при необходимости проверить доступ к сети кластера или VPN. Новая попытка с Codex требует разового разрешения.

## Синхронизация кода

На Mac сначала выполнить `git status --short --untracked-files=all`, `git rev-parse HEAD` и `git diff --check`. На сервере прочитать ветку, коммит, `git status` и очередь пользователя:

```bash
ssh -o BatchMode=yes -o ConnectTimeout=10 zhores '
  cd /gpfs/gpfs0/ajnaz.gibadullin/InverseProblems || exit 1
  git rev-parse HEAD
  git branch --show-current
  git status --short --untracked-files=all
  squeue -r -u "$USER" -o "%.18i %.22j %.12T %R"
'
```

Одинаковый HEAD не исключает правок в рабочей копии. Для файлов, которые изменились с обеих сторон, посмотреть diff перед заменой. Когда пользователь просит запускать локальную версию кода, переносить согласованный список путей и сохранять прежние серверные версии конфликтующих файлов, если они нужны для отката. Учитывать активные задания, которые могут читать тот же исходный код или конфиг. Новые локальные файлы переносить явным списком. Данные, `runs/`, `.venv` и `.git` в обычную синхронизацию кода не входят.

Пример команды переноса **с Mac** с сохранением относительных путей. Список путей в конкретной операции составить по фактическим изменениям:

```bash
rsync -acvR --no-implied-dirs \
  -e 'ssh -o BatchMode=yes -o ConnectTimeout=10' \
  configs/celeba_medium_abm_T1.yaml scripts/train_abm_slurm.sh \
  zhores:/gpfs/gpfs0/ajnaz.gibadullin/InverseProblems/
```

`--no-implied-dirs` сохраняет серверные атрибуты родительских папок при передаче отдельных файлов с `-R`. Для операции с резервной копией можно включить `--backup --backup-dir=/абсолютный/серверный/путь` и показать этот путь в запросе разрешения. Для новых файлов `--ignore-existing` позволяет защитить одноимённый серверный файл от перезаписи, после чего его содержимое обязательно проверить. Узкую передачу сверять через локальный `shasum -a 256` и серверный `sha256sum`. При необходимости отдельно подтвердить, что Python внутри контейнера импортирует код из `/workspace/src/`.

При последней полной синхронизации мы сверяли SHA-256, проверяли импорт `bridge_restore.training` в контейнере и сохраняли прежние файлы сервера в `runs/.repo_sync_backup_20261121-000800/`. Текущая рабочая копия на Mac содержит более новые изменения, поэтому и код, и конфиги в следующем задании нужно сверять заново.

Пример проверки импорта **на сервере**, из корня репозитория, без выделения GPU:

```bash
apptainer exec --bind "$PWD:/workspace" --pwd /workspace \
  /trinity/home/ajnaz.gibadullin/sif_containers/es-bench.sif \
  bash -c 'source .venv/bin/activate && PYTHONDONTWRITEBYTECODE=1 python -c "from bridge_restore import training; print(training.__file__)"'
```

## Запуск через Slurm

Для BM/ABM на обучении использовался `ais-gpu` с A100. В этой группе сервер выводил правило распределения ресурсов на GPU, поэтому фактически выделенные CPU и RAM смотреть в Slurm, даже если в скрипте записаны другие запрошенные значения. Для коротких тестов использовались GTX 1080 Ti на узле `vt01` в разделе `gpu_devel`. В Slurm тип указан как `geforce` и включает также RTX 2080 Ti. Если нужна именно 1080 Ti, указывать `vt01` и проверять фактическое имя GPU. Доступность узлов и лимиты проверять по текущему состоянию:

```bash
sinfo -p ais-gpu,gpu_devel -N -o "%P %N %G %l %t"
```

Команды ниже выполняются **на сервере из корня репозитория** после подтверждения:

```bash
cd /gpfs/gpfs0/ajnaz.gibadullin/InverseProblems
sbatch --parsable scripts/train_slurm.sh train configs/celeba_medium_abm_T1.yaml
```

Этот пример показывает синтаксис. Для нового обучения использовать свободный `output_dir` и актуальный конфиг. Уже заполненный каталог обычный `bridge_restore.train` отвергнет без `--resume`. Повторять подачу после обрыва SSH только после проверки очереди и `sacct`, поскольку Slurm мог уже принять первое задание. Режим продолжения применять только если он нужен пользователю и подходит к конкретному чекпойнту.

| Скрипт | Назначение |
|---|---|
| [train_slurm.sh](../scripts/train_slurm.sh) | Базовый запуск BM/ABM через `srun` внутри контейнера. Аргументы `train CONFIG` для одной модели и `grid CONFIG` для сетки. |
| [train_bm_low_noise_slurm.sh](../scripts/train_bm_low_noise_slurm.sh) | Индексы массива 0 и 1 соответствуют BM `T=0.6` и `T=0.8`. |
| [train_abm_slurm.sh](../scripts/train_abm_slurm.sh) | Индексы 0, 1 и 2 соответствуют ABM `T=1`, `T=1.25` и `T=1.5`. |
| [sweep_steps_test.sh](../scripts/sweep_steps_test.sh) | Тест числа шагов. Принимает папку исходного обучения и папку результатов. Для 1080 Ti явно указывать `--nodelist=vt01`. |
| [seed_diversity_test.sh](../scripts/seed_diversity_test.sh) | Тест разнообразия. Аргументы `source_root`, `output`, `k` и необязательное имя одной модели. По умолчанию проверяет шесть моделей старой сетки. |

Для строгого порядка мы подавали отдельные элементы массива и связывали их через `--dependency=afterany:<ID>`. Тогда следующее задание разблокируется при любом исходе предыдущего. Для продолжения только после успеха используется `afterok`. Суффикс `%1` в массиве ограничивает одновременное выполнение, а строгий порядок задаётся зависимостью.

Пример синтаксиса для двух последовательных элементов. Подставлять скрипт и индексы **новой** серии после проверки её выходных путей. `sbatch --parsable` может вернуть `ID;имя_кластера`, поэтому в зависимость передаётся часть до точки с запятой:

```bash
first=$(sbatch --parsable --array=0 scripts/train_bm_low_noise_slurm.sh) || exit 1
first_id=${first%%;*}
sbatch --parsable --array=1 --dependency="afterany:$first_id" scripts/train_bm_low_noise_slurm.sh
```

Для новой ветки экспериментов сначала сверить её собственную документацию и фактическую точку входа. Например, локальная [инструкция SOC](soc_training.md) описывает `bridge-soc-train` и отдельный протокол. Совместимость серверной `.venv` с новыми extra и наличие кода проверяются отдельно. Запуск BM/ABM сам по себе этого не подтверждает.

## Статус и прогресс

На сервере:

```bash
squeue -r -u "$USER" -o "%.18i %.22j %.12T %.12M %.12L %R"
sacct -X -j "$job_id" -n -P --format=JobID,State,Elapsed,Timelimit,ExitCode
```

`PENDING` с причиной `Priority` означает ожидание в очереди. `Dependency` означает, что ещё не выполнена зависимость. `RUNNING` означает выделение ресурсов, а начало собственно расчёта подтверждается стартовым логом. После ухода задания из очереди статус берётся из `sacct`. Для успешного результата сверить `COMPLETED`, код выхода и сами выходные файлы. `TIMEOUT` может оставить частично рассчитанный эксперимент.

Логи лежат в корне серверного репозитория. Для одиночного задания шаблон `slurm-<имя>-<ID>.out` и `.err`. Для массива используется `slurm-<имя>-<ID массива>_<индекс>.out` и `.err`. Прогресс `tqdm` содержит возвраты каретки, поэтому удобно читать конец небольшим фрагментом:

```bash
tail -c 7000 "$err_log" | tr '\r' '\n' | tail -n 12
tail -n 8 "$out_log"
```

В BM/ABM смотреть `metrics.jsonl`, папки `validation/epoch_*` и финальный `test/lpips/`. Эпоха из `test/lpips/protocol.json` относится к чекпойнту, выбранному на валидации. Число реально завершённых эпох берётся из логов валидации и `completed_epochs`. В пяти новых обучениях был `early_stopping_patience: 4`. Текущая реализация срабатывает после пятой эпохи без улучшения LPIPS. В последних парах запусков эта отметка иногда совпадала с лимитом в 15 эпох.

Признаки готового отчёта BM/ABM:

- `best/lpips/checkpoint.pt` существует, если для работы нужен сам чекпойнт.
- В `test/lpips/` есть `summary.json`, `protocol.json` и `per_image.jsonl`. Число строк сверяется с `samples` в сводке. У пяти последних запусков это 1 024.
- Визуальные PNG лежат в `test/lpips/images/`. `best/lpips/images/` относится к валидации выбранной эпохи.

В тестах числа шагов финиш отмечен `SWEEP_COMPLETE`. Проверялось наличие восьми панелей и пяти строк данных в `comparison.csv`. В тесте разнообразия ориентиры — `DIVERSITY_SEED_DONE`, `DIVERSITY_MODEL_DONE` и `DIVERSITY_COMPLETE`, затем сверка чисел в CSV и количества PNG с протоколом.

## Скачивание результатов

Сначала проверить наличие итогового отчёта и локальный путь назначения. Хранить результаты в `runs/`, по возможности с теми же относительными путями, что на сервере. Для узкой выгрузки перечислять точный файл или одну папку. Для передачи целого эксперимента использовать `rsync --partial`, чтобы при обрыве повторный вызов мог использовать уже полученные данные.

Пример **на Mac** для полной папки одного запуска. Перед выполнением проверить, нужна ли передача именно в этот локальный путь:

```bash
mkdir -p runs/celeba_abm_b128_15ep
rsync -a --partial --stats --timeout=180 \
  -e 'ssh -o BatchMode=yes -o ConnectTimeout=10 -o ServerAliveInterval=30' \
  zhores:/gpfs/gpfs0/ajnaz.gibadullin/InverseProblems/runs/celeba_abm_b128_15ep/medium_abm_T1.25/ \
  runs/celeba_abm_b128_15ep/medium_abm_T1.25/
```

Завершающий `/` у источника означает копирование содержимого в указанную папку. Если пользователь просит оставить только тестовые картинки, при передаче папки одного запуска добавить `--exclude='/validation/*/images/'` и `--exclude='/best/*/images/'`. Чекпойнт, метрики и протоколы при этом копируются. Если требуется только таблица, передавать непосредственно CSV. Файлы `.fp32/` в тестах разнообразия нужны для расширения числа seed и увеличивают объём выгрузки. Их включение обсуждается отдельно, когда пользователь просит только сводку или PNG.

При долгой передаче сообщать объём полученных данных примерно каждые две минуты. Скорость соединения менялась даже в рамках одного скачивания, поэтому оценку оставшегося времени уточнять по фактическому прогрессу. После успешной передачи сверить число и размер файлов с итогом `rsync`, прочитать JSON/CSV и при необходимости проверить PNG. При обрыве сохранить частичные файлы и повторить операцию после восстановления соединения и нового разрешения.

## Удаление и отчёт пользователю

При удалении сначала снять инвентарь `runs/`, проверить очередь и отделить запуски обучения от тестов, кэшей и резервных копий по путям и артефактам. Показать точный список удаляемых серверных каталогов, указать, какие эксперименты сохраняются, и отдельно получить разрешение на удаление. При наличии локальной копии подтвердить её по чекпойнту и отчёту. После удаления проверить отсутствие выбранных путей и наличие сохранённых результатов.

В итоговом сообщении указывать фактически проверенное состояние, ID, точный путь и нужные пользователю числа. Для скачанного результата давать ссылку на локальную папку. Для статуса полезно отдельно указать завершённые эпохи, эпоху чекпойнта, стадию теста и причину ожидания или остановки. Состояние очереди, наличие файлов и скорость передачи брать из новой проверки, когда пользователь спрашивает об их текущем состоянии.
